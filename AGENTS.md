# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project Overview

Personal portfolio and blog of Ariane Brandão (front-end developer / software engineer), published at **https://arianebrandao.github.io** via **GitHub Pages**. It is a static **Jekyll** site based on the [Indigo theme](https://github.com/sergiokopplin/indigo), customized through the repo's own `_layouts/` and `_includes/`. All site content (posts, pages, bio) is written in **Brazilian Portuguese (pt-BR)**.

## Commands

| Purpose                   | Command                                                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Install Ruby dependencies | `bundle install`                                                                                                                           |
| Dev server                | `bundle exec jekyll serve --config _config.yml,_config-dev.yml` → http://localhost:4000                                                    |
| Build                     | `bundle exec jekyll build` (output to `_site/`)                                                                                            |
| Validate links            | `bundle exec rake test` (builds the site and runs htmlproofer — the Rakefile is the single source of truth for the flags, and CI calls it) |
| Build CSS                 | `npm run build:css` (compila `assets/css/tailwind.css` → `assets/css/style.min.css`; commite o resultado)                                  |
| Watch CSS                 | `npm run watch:css`                                                                                                                        |
| Scaffold a new post       | `./initpost.sh -c "Post Title"`                                                                                                            |

There is no Ruby on this machine — run the Ruby commands inside the podman container described in `README.md` (dev server) or in the `validate-site` skill (build + link checks). Node/npm are needed on the host only for the Tailwind build, in version 26 (declared in `engines` in `package.json`).

The htmlproofer flags (defined only in the `Rakefile`) match what CI runs: `Links`, `Scripts` and `Images` are checked (lazyload `data-src` is swapped into `src`), HTTPS is enforced, and 403/999 status codes are ignored (bot walls like winehq.org and LinkedIn). Dead legacy client domains listed in the `Rakefile` are ignored too — remove an entry when the link is updated or dropped. `baseurl: ""` is set explicitly in `_config.yml` because `jekyll-github-metadata` otherwise injects a `/pages/arianebrandao` fallback when building locally without `JEKYLL_GITHUB_TOKEN`. The `drive.google.com/open?id=1UUmS1cI...` ignore is a known-dead link in the Warframe post, pending a replacement.

## Repository Structure

- `_config.yml` — site-wide config: identity/bio, social links, Google Analytics, Disqus, feature flags (`projects`, `about`, `blog`, `contact`), permalink (`/:title/`), plugin list.
- `_config-dev.yml` — dev override (`url: http://localhost:4000`); used by the serve command above.
- `_posts/` — blog and portfolio posts (Markdown, see conventions below).
- `_layouts/` — page templates (`default`, `home`, `page`, `post`, `compress`). This is the real "theme".
- `_includes/` — reusable partials (nav, footer, social links, analytics, Disqus, etc.).
- `assets/` — `css/` (`tailwind.css` is the Tailwind source; the served and committed `style.min.css` is built with `npm run build:css`), `js/` (`lazysizes.min.js`), `images/` (post images under `assets/images/posts/<name>/`).
- Top-level pages: `index.html`, `about.md`, `contact.html`, `projects.html`, `blog/`, `tags.html`, `404.html`, `notallowed.html`.
- `.github/workflows/ci.yml` — CI pipeline (see CI & Deployment).
- `initpost.sh` — post scaffolding script.
- `.ruby-version` — Ruby version used by local tooling (CI sets `ruby-version: '3.2'` explicitly).
- `sitemap.xml` and `feed.xml` are generated by `jekyll-sitemap`/`jekyll-feed` at build time — never commit static copies of them.

## Content Conventions

Posts live in `_posts/` and follow the filename pattern `YYYY-MM-DD-slug.md`. There are two front-matter shapes — copy from an existing post of the same kind:

**Blog post** (tutorial/experience, shown on the blog):

```yaml
---
title: "Post title"
layout: post
date: YYYY-MM-DD HH:MM
headerImage: false
tag:
  - tag1
  - tag2
category: blog
author: arianebrandao
description: Short description
---
```

**Project/portfolio post** (shown in Projects; not counted in blog pagination):

```yaml
---
title: "[Portfólio] Project Name - Tech"
layout: post
date: YYYY-MM-DD HH:MM
tag:
  - projetos
  - portfolio
image: https://arianebrandao.github.io/assets/images/posts/<name>/1.png
headerImage: true
projects: true
hidden: true
description: "Portfólio: Project Name"
category: project
author: arianebrandao
externalLink: false
comments: true
---
```

- Always set `author: arianebrandao` (must match the `authors` map in `_config.yml`).
- Write new content in **pt-BR**.
- Reference site URLs/images with `{{ site.url }}` (e.g. `{{ site.url }}/assets/images/posts/<name>/2.png`). For screenshots use the lazyload pattern: `<img data-src="{{ site.url }}/assets/images/posts/<name>/1.png" class="lazyload" alt="..." />` inside `<p align="center">`, plus a `<noscript>` fallback with plain `src`, and a `<figcaption class="caption">`. Assets referenced from `_layouts/` or `_includes/` must use `relative_url` (e.g. `{{ '/assets/css/style.min.css' | relative_url }}`) so the local preview resolves against `localhost`.
- Permalinks are generated as `/:title/` — links between posts use the slugified title (e.g. `https://arianebrandao.github.io/bootloader-unlocker-root-umidigi-power-3/`).

## CI & Deployment

`.github/workflows/ci.yml` (GitHub Actions) runs on every push to `main` or `dev` and on pull requests: `npm ci` + `npm run build:css` (Node 26), a `git diff --exit-code -- assets/css/style.min.css` guard, then `bundle install` (Ruby 3.2, gems cached via `bundler-cache`) and `bundle exec rake test` (`JEKYLL_GITHUB_TOKEN` set) — the Rakefile builds the site (`JEKYLL_ENV=production`) and runs htmlproofer with the flags documented in Commands. There is no deploy step — GitHub Pages builds and serves the site natively on push to `main`. The `bundler-cache` step installs gems into `vendor/bundle` inside the workspace — `_config.yml` excludes `vendor` (and `Rakefile`, `node_modules`, `package.json`) because of that, otherwise Jekyll scans them as site content and the build fails. Broken links (any non-ignored status, DNS failure or timeout), missing images, non-HTTPS references and a stale committed CSS fail CI — verify any external/edited URLs in posts and rerun `npm run build:css` after changing classes.

## Gotchas

- **CSS is compiled and committed**: `assets/css/tailwind.css` is the source; the site serves `assets/css/style.min.css`, built with `npm run build:css` and **committed** (GitHub Pages does not run a CSS build). CI fails if the committed file is stale.
- **Node tooling is CSS-only**: `package.json`/`node_modules` exist for Tailwind; Jekyll still builds with Bundler. Bulma was removed in favor of Tailwind utilities plus a small component layer in `tailwind.css`.
- Changes to `_config.yml` require restarting the dev server; most other files hot-reload.
- The `github-pages` gem pins the Jekyll/plugin versions — prefer plugins already listed in `_config.yml`.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) — see `.agents/rules/conventional-commits.md` for the allowed types, scopes, and format (e.g. `docs: update about me`).
- **Never commit, push, tag or open a PR without an explicit request** — finishing a plan, passing tests or closing all TODOs is not authorization. Stop after validating and let the diff be reviewed. See `.agents/rules/git-workflow.md`.
- **Work on `dev`**: all work happens on the `dev` branch. When implementing a plan, ask whether to create a dedicated branch (`git switch -c <type>/<slug>`) or continue on `dev` before the first edit — never create a branch on your own. If work started on the wrong branch by mistake, move it with `git switch -c` instead of committing.
- **Commits are delegated to the `commit-writer` subagent** (`.commandcode/agents/commit-writer.md`) — whenever the user asks to commit, hand the task to it instead of running `git commit` yourself.

## Learning Loop

At the end of a significant task (multi-step work, a new workflow, or anything that required non-obvious setup discovered by trial and error), pause and review the process before finishing:

- If a step was repetitive, error-prone, or had non-obvious reasoning (environment quirks, flags whose purpose is not self-evident), propose capturing it: update this AGENTS.md, or create/update a skill in `.agents/skills/` (one capability per skill; use the `skill-writer` skill to author it). This prevents the next session from rediscovering the same pitfalls.
- Always ask the user before creating or updating these files.
- Example: the container-based local validation workflow was captured this way as the `validate-site` skill.
